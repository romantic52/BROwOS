# Разработка BROwOS

Официальный репозиторий: [romantic52/BROwOS](https://github.com/romantic52/BROwOS). `main` должна содержать собираемую версию. Новую функциональность разрабатывают в тематической ветке этого проекта и объединяют после проверки через Pull Request.

## Начало работы

```bash
git clone https://github.com/romantic52/BROwOS.git
cd BROwOS
npm install --global pnpm@10.34.7
pnpm install --frozen-lockfile
pnpm dev
```

Требуется Node.js 22.12+ или Node.js 24. Frontend доступен на `http://localhost:5173`. Для обычной Local Edition сервер не нужен. Connected требует отдельного Chromium runtime; смотрите [документацию сервера](docs/CONNECTED.md).

## Изменение подсистемы

1. Создайте или уточните Issue: цель, техническое описание, критерии готовности, зависимости и тестовые сценарии.
2. Создайте ветку `feature/<subsystem>`, `fix/<problem>` или `refactor/<scope>`. Сохраняйте существующую историю; force push в `main` не используется.
3. Реализуйте наблюдаемое поведение. Используйте общие VFS, Window Manager и SDK вместо отдельных несвязанных хранилищ внутри приложений.
4. Добавьте регрессионный тест для изменённого поведения. Сохранения, миграции и файловые операции требуют проверки данных после повторного открытия, а не только проверки формы ответа.
5. Запустите нужные проверки, затем общий `pnpm check`, аудит и E2E по [TESTING.md](docs/TESTING.md).
6. Обновите документацию, changelog и `docs/DEVELOPMENT_STATUS.md`: реализованное поведение, ограничения, Issue/PR и фактические результаты.
7. Создайте Conventional Commit и PR. Укажите, какую проблему решает изменение, как изменится поведение и что выполнено для проверки.

Примеры коммитов:

```text
feat(explorer): preserve imported filenames on collisions
fix(notepad): reject stale document saves
test(browser): cover local tab navigation
docs: document Connected deployment requirements
```

Не закрывайте Issue до выполнения её критериев. При проблеме с окружением фиксируйте `BLOCKED` и конкретную причину. Не заменяйте неработающую возможность ложной кнопкой, случайными метриками или изображением интерфейса.

## Границы модулей

- `apps/web` — загрузка, desktop shell, общие диалоги и композиция приложений.
- `packages/filesystem` — транзакционная VFS и постоянное хранение в IndexedDB.
- `packages/window-manager` — состояние окон, фокус, геометрия и рабочие столы.
- `packages/application-runtime` и `packages/sdk` — регистрация приложений и сервисы общего рабочего стола.
- `system-apps` — приложения, использующие общие сервисы.
- `apps/server` — аутентифицированный Connected Chromium runtime и сетевые ограничения.
- `tests` — проверки пользовательского поведения и взаимодействия подсистем.

Приложения BROwOS — доверенные модули одного frontend. SDK не является границей изоляции недоверенного кода. Новые приложения не должны получать возможность исполнять системные команды, обходить правила сетевого runtime или незаметно отправлять локальные файлы на сервер.

## Данные и интерфейс

Операции VFS сохраняют содержимое, происхождение и связи элементов. При редактировании открытого файла используйте проверку версии, чтобы не перезаписать более новое сохранение из другого окна или вкладки. Закрытие редактора с несохранёнными изменениями должно дать пользователю возможность остаться в документе.

Интерфейс использует русский язык, доступные имена элементов и управление с клавиатуры. Проверяйте изменение размеров окна, фокус, небольшую ширину и режим reduced motion. Скриншоты PR должны быть получены из запущенного приложения.

Local-режим выполняется в браузере и подчиняется его ограничениям хранения, iframe, autoplay и поддержки кодеков. Connected запускает отдельный Chromium на сервере. Remote VM — самостоятельная задача и не считается реализованной через iframe или desktop wallpaper.

## Секреты и зависимости

Не добавляйте `.env`, токены, browser profiles, приватные ключи или личные файлы в Git. Демо и тесты используют явно обозначенные фикстуры. Переменные `VITE_*` попадают в публичный frontend и не подходят для секретов.

Проверяйте обновления lockfile и Dependabot PR теми же тестами. Ошибка аудита — причина исследовать зависимость и исправление; автоматическое ослабление порога аудита не заменяет анализ. Уязвимости отправляйте по [SECURITY.md](SECURITY.md).
